# Automation Animation Initialization Debug Notes

Date: 2026-08-19

## Current implementation trace

The animation is implemented in `HeroAutomationAnimation.tsx` with a `useEffect` hook that queries the mounted stage, AI core, SVGs, and 13 node cards. It registers pointer, resize, and reduced-motion listeners, then schedules an `initialFrame` via `requestAnimationFrame`. That callback calls `refreshGeometry()` and conditionally invokes `startLoop()`. `startLoop()` schedules the first `tick`, and each non-reduced-motion tick updates node transforms, recalculates path geometry, and schedules the next frame.

The current live measurement after mount showed the first node transform changed over 450 ms while the page was visible, with 13 nodes present and `prefers-reduced-motion` false. This proves the loop can run automatically on an already-mounted page, but it does not yet prove reliable behavior during the first hydration/paint window, fresh load, or hard refresh.

## Suspected lifecycle weakness

The startup path is split across nested requestAnimationFrame callbacks: the first callback performs geometry initialization and then schedules the actual animation loop. The loop also depends on the first callback finding all queried DOM elements and on the initial reduced-motion value. There is no explicit startup state, no visibility recovery path, and no instrumentation that distinguishes a loop that never started from one that was canceled during hydration or navigation.

The next step is to make startup idempotent and explicit: initialize geometry after the DOM is ready, start exactly one RAF loop immediately, recover on visibility changes, and retain cleanup guards so remounts cannot create duplicate loops.
